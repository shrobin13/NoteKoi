## 1. Project Rules (Non-Negotiable)

- Never create an API not derivable from `userflow.md`.
- Never add a database field, model, enum, or relation not present in `schema.prisma`.
- Never invent roles, permissions, states, transitions, or notification events.
- Never skip Zod validation on any input surface (body, params, query).
- Never write business logic inside a route handler or controller — controllers call services only.
- Never access `PrismaClient` from a controller or route — only repositories touch Prisma.
- Never bypass authentication, role checks, or ownership checks, even for "internal" or "admin" routes — apply the correct guard explicitly.
- Never return a raw Prisma/DB error or stack trace to the client — map to the standard error envelope (Section 8).
- Never hardcode IDs, role strings, or magic numbers — use `constants/` and enums generated from `schema.prisma`.
- Never skip a DB transaction where a workflow touches more than one table with a consistency requirement (e.g., resource state change + notification + promotion-recommendation invalidation).
- Never silently drop the "one active X" business rules that Prisma cannot express natively (one active Sub Admin per college; one active CR + one active Co-CR per Department+Session; one PENDING promotion recommendation per resource) — enforce at the application layer inside the same transaction that would violate them, AND add the raw partial-unique-index migrations called out in `schema.prisma` comments as a second line of defense.
- Never physically delete an uploaded file from storage without first checking whether another `Resource` row still references the same `contentHash` (§5.6, §8) — dedup means one file can back many records.
- Always keep controllers thin: parse → call service → format response.
- Always put business logic in `services/`, DB access in `repositories/`.
- Always use dependency separation: routes → controllers → services → repositories → Prisma.
- Always finish and pass Section 15's Done Criteria for one feature before starting the next.

## 3. Coding Standards

**Naming**
- Files: `camelCase.ts`. Classes: `PascalCase`. Functions/vars: `camelCase`. Constants: `UPPER_SNAKE_CASE`.
- Route files match Prisma model plural (`resources.routes.ts`), service/repo match singular module (`resource.service.ts`, `resource.repository.ts`).

**Imports**
- Absolute imports via `tsconfig` path aliases (`@services/*`, `@repositories/*`) — no `../../../`.
- Never import Prisma client outside `repositories/`.

**Dependency flow (one direction only)**
`routes → controllers → services → repositories → prisma`. Services may call other services (e.g., `resourceService` calls `notificationService`); repositories never call services.

**Error handling**
- Throw typed errors from `errors/` in services; never `res.status(...)` inside a service.
- Single centralized error middleware converts thrown errors to the standard error envelope (Section 8).

**Response format**
- Every controller returns via a shared `helpers/response.ts` formatter — never `res.json({...})` ad hoc.

**Transactions**
- Any service method that (a) changes `Resource.state` and touches another table, or (b) creates/revokes a role assignment, or (c) resolves a report/deletion request together with a moderation decision, must wrap the writes in `prisma.$transaction`.

**Logging**
- Winston/Pino logger injected via `config/logger.ts`. Use `logger.info/warn/error`, never `console.log` in `src/`.

**Enums**
- Mirror `schema.prisma` enums via Prisma's generated types — never redeclare enum string literals by hand in TS.

**Constants**
- `constants/adminOverrideActions.ts` — whitelist of allowed `AdminOverrideLog.action` strings per `overrideType`, since the schema stores these as free-text (`schema:AdminOverrideLog`) and hallucinated/inconsistent values must be prevented at the app layer.

**Environment variables**
- All secrets/config via `.env`, loaded and validated at boot with Zod (`config/env.ts`) — app must fail fast on missing/invalid env vars.
- Required keys (minimum): `DATABASE_URL`, `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET`, `JWT_ACCESS_EXPIRY`, `JWT_REFRESH_EXPIRY`, `COOKIE_DOMAIN`, `SMTP_HOST`/`SMTP_PORT`/`SMTP_USER`/`SMTP_PASS`, `MAX_FILE_SIZE_MB` (default `20`), `ALLOWED_MIME_TYPES` (comma-separated), `ADMIN_EMAIL`, `ADMIN_PASSWORD` (used only by the Phase 1/5 seeder — see Section 7).

**Service pattern**
- One service per Prisma model/domain concept; a service method = one business operation, always returning a plain DTO, never a raw Prisma object with unrelated internal fields leaked (e.g. never leak `passwordHash`).

**Repository pattern**
- One repository per Prisma model; methods are thin CRUD + targeted queries (no business rules, no cross-model orchestration).

**Controller pattern**
- `async (req, res, next) => { try { const dto = await service.doThing(...); res.json(ok(dto)); } catch (e) { next(e); } }` — no try/catch business branching beyond this shape.

**Middleware pattern**
- Order per route: `validate(schema) → authenticate → authorize(role/permission) → ownership/scope guard → controller`.

**Dependency injection**
- Simple constructor/factory injection is sufficient (no DI framework required) — services receive repositories as constructor args to keep them unit-testable.

**Module organization**
- Group by domain (auth, users, colleges, departments, sessions, courses, resources, moderation, promotion, reports, deletionRequests, notifications, analytics, admin) — one Phase in Section 11 maps to one module.

## 4. API Standards

- **Base path:** `/api/v1`.
- **REST naming:** plural nouns (`/resources`, `/colleges`), nested only where ownership is hierarchical (`/colleges/:collegeId/departments`).
- **Versioning:** path-based (`/api/v1`), bump on breaking change only.
- **HTTP methods:** `GET` read, `POST` create/action, `PATCH` partial update, `DELETE` soft/hard delete per business rule (most deletes here are state transitions via `POST`, e.g. `POST /resources/:id/request-deletion`, not raw `DELETE`).
- **Status codes:** `200` ok, `201` created, `204` no content, `400` validation, `401` unauthenticated, `403` forbidden (role/ownership), `404` not found, `409` conflict (state/business rule), `422` unprocessable (semantic validation), `500` unexpected (never leaks internals).
- **Pagination:** `?page=1&limit=20` query params, response includes `{ data, meta: { page, limit, total, totalPages } }`.
- **Filtering:** `?resourceType=&courseId=&sessionId=&visibility=` per §2.3.
- **Searching:** `?q=` matches course name / keyword / resource type per §2.2.
- **Sorting:** `?sortBy=createdAt&order=desc` (default `createdAt desc`).
- **Request validation:** Zod schema per route for `body`, `params`, `query` — reject unknown keys (`.strict()`).
- **Success response:**
```json
{ "success": true, "data": {}, "meta": { } }
```
- **Error response:**
```json
{ "success": false, "error": { "code": "VALIDATION_ERROR", "message": "human readable", "fields": [ { "field": "email", "message": "Invalid email" } ] } }
```
- **File upload conventions:** `multipart/form-data` via Multer, disk storage under `storage/uploads/<collegeId|platform>/<resourceId>/`, reject unsupported MIME types and oversized files at the Multer layer per §3.4 before hitting the controller.
  - **Max file size: 20 MB per file** (`MAX_FILE_SIZE_MB=20` in `.env`, read by `config/storage.ts`, enforced via Multer's `limits.fileSize`) — confirmed value, not a placeholder.
  - **Allowed MIME types (default whitelist, config-driven via `ALLOWED_MIME_TYPES`):** `application/pdf`, `application/msword`, `application/vnd.openxmlformats-officedocument.wordprocessingml.document`, `application/vnd.ms-powerpoint`, `application/vnd.openxmlformats-officedocument.presentationml.presentation`, `video/mp4`, `video/quicktime`, `image/jpeg`, `image/png`. Reject anything else with `400 UNSUPPORTED_FILE_TYPE`.

## 5. Validation Standards

- Every route validates `body`, `params`, and relevant `query` with Zod — no exceptions.
- Every validation failure returns:
```json
{ "field": "sessionId", "message": "sessionId is required for PYQ resources", "code": "REQUIRED_FOR_TYPE" }
```
- Cross-field/business validations to encode explicitly in Zod `.refine()` / `.superRefine()`:
  - `resourceType = PYQ` ⇒ `sessionId` required (§3.3).
  - `resourceType = VIDEO` ⇒ exactly one of `fileUrl` (uploaded file) or `youtubeUrl` present, never both required (§3.3).
  - Non-video types ⇒ `fileUrl` required, `youtubeUrl` must be absent.
  - Student upload ⇒ server forces `visibility = COLLEGE`, `collegeId = student's collegeId`; reject any client-supplied `visibility = PLATFORM` (§0.2 Student, §3.1).
  - Teacher upload ⇒ `visibility` may be `COLLEGE` (default) or `PLATFORM`, chosen by client, but Teacher must not be `PENDING_VERIFICATION` (§1.3, §5.8).
  - Structural edit (`courseId`/`departmentId` change) ⇒ new course's department must be within uploader's allowed department scope (own department for Student; assigned departments for Teacher) — reject at validation/service layer (§3.6, §8).
  - `regNo` uniqueness is scoped to `(collegeId, regNo)`, not globally (§1.2, `schema:User @@unique([collegeId, regNo])`).
- Never trust any client-sent `state`, `visibility` (beyond the Teacher upload-time choice), `uploaderId`, `moderatorId`, or role field — these are always server-derived from the authenticated session or business rule, never accepted raw from the request body.
- Backend is the sole source of truth; frontend validation (Next.js/shadcn) is UX-only and must be fully re-validated server-side.

## 6. Authentication & Authorization

**Implementation order:**

1. Password hashing utility (bcrypt).
2. JWT utilities: access token (short-lived) sign/verify.
3. Refresh token strategy — a separate, longer-lived, separately-signed JWT (no DB table exists for it, see Section 16 §1). Both access and refresh tokens are delivered as **httpOnly, secure, sameSite=strict cookies** (decision — see Section 16 §6), not as bearer tokens in the response body. Rotated on every `/auth/refresh` call.
4. Login (email + password, any role, single `User` table) — sets the access-token cookie and refresh-token cookie; response body carries only the user profile DTO (never `passwordHash`, never the raw tokens — they live in cookies only).
5. CSRF protection — since cookies now carry auth, issue a non-httpOnly CSRF token cookie at login and require it echoed back in an `X-CSRF-Token` header on every state-changing request (`POST`/`PATCH`/`DELETE`); verified by a dedicated `csrfGuard` middleware (double-submit cookie pattern). This is mandatory, not optional, because cookie-based auth was chosen.
6. Logout (clears both cookies server-side via `Set-Cookie` with `maxAge=0`; document the statelessness limitation — see Section 16 §1).
7. Forgot Password (issue short-lived signed reset token via email, Nodemailer) — stateless, no DB table (Section 16 §1).
8. Reset Password (verify signed token, update `passwordHash`).
9. Session validation middleware (`authenticate`): reads the access-token cookie, verifies it, attaches `req.user` (id, role, collegeId, departmentId, sessionId as applicable).
10. Role-Based Access middleware (`authorize(...roles)`): checks `req.user.role` against `schema:Role` enum values (`PLATFORM_ADMIN`, `SUB_ADMIN`, `STUDENT`, `TEACHER`). **Important:** for `SUB_ADMIN`-gated routes, a matching `role` alone is not sufficient — also require an **active** `SubAdminAssignment` for that user (see Section 16 §2, since `User.role` has no way to "revert" after a promotion is later revoked).
11. Permission/elevation middleware for CR/Co-CR: since CR/Co-CR is not a `Role` value but an active `CrCoCrAssignment` row, build a dedicated `requireActiveCrCoCr(departmentId?, sessionId?)` guard that checks for an `isActive = true` assignment matching the resource's Department+Session (§0.2, `schema:CrCoCrAssignment`).
12. Ownership validation middleware: compares `req.user.id` to `resource.uploaderId` for uploader-only actions (versioning, metadata edit, self-deletion) — ownership is by **original uploader**, never current role (§3.5).
13. Scope guards: `sameCollegeGuard` (Sub Admin vs resource.collegeId), `deptSessionGuard` (CR/Co-CR vs resource.departmentId + sessionId) — used on every moderation/queue endpoint.
14. Route guards composed per endpoint from the above (never ad hoc inline checks in a controller).

## 7. Database Standards

Every DB-related task below is stated as **Task → Why**, so the reasoning is never left implicit.

- Follow `schema.prisma` exactly — it is immutable input to this project; never edit it to "make a feature easier." If a feature appears to need a field that doesn't exist, stop and record it under Section 16, do not add the field.
  - **Why:** `schema.prisma` is the canonical spec's database half; silently patching it re-introduces exactly the hallucination risk this whole file exists to prevent.

- **Task — Transactions:** wrap every multi-table write described in Section 3 ("Transactions") in `prisma.$transaction`.
  - **Why:** several workflows (approve + supersede prior version, revoke + queue transfer, structural edit + promotion invalidation) must never leave the DB half-updated if one write fails mid-way.

- **Task — Relations:** respect every named relation exactly as declared (`"ResourceVersions"`, `"UploaderResources"`, `"ModeratedResources"`, `"CrCoCrUser"`, etc.) — do not create parallel ad hoc joins.
  - **Why:** the schema already disambiguates multiple relations between the same two models (e.g. `User` ↔ `Resource` via both `uploaderId` and `moderatorId`); an ad hoc join risks joining on the wrong FK.

- **Task — Indexes:** rely on the declared `@@index`/`@@unique` for query planning; do not add new indexes without flagging a schema-change request to the human maintainer.
  - **Why:** indexes are part of the immutable schema contract, same reasoning as the top rule.

- **Task — Soft delete:** there is no boolean soft-delete flag; deletion is modeled as `ResourceState.DELETED` (a state, not a row removal) — never call `prisma.resource.delete()` in application code, always update `state`.
  - **Why:** §5.1's state machine treats `Deleted` as a terminal *state*, not a row-removal event; hard-deleting the row would break Version History (§6) and moderation audit trails that must still reference it.

- **Task — Enums:** use Prisma-generated enum types directly; never hand-roll parallel string unions.
  - **Why:** a hand-rolled union can drift from the schema's enum values over time with no compiler error to catch it.

- **Task — Partial-unique business rules (not expressible in core Prisma) — enforce in the service layer inside the same transaction, AND add via a raw SQL migration:**
  - One `isActive = true` `SubAdminAssignment` per `collegeId`.
  - One `isActive = true` `CrCoCrAssignment` per `(collegeId, departmentId, sessionId, type)`.
  - One `PENDING` `PromotionRecommendation` per `resourceId`.
  - **Why:** `schema.prisma`'s own comments flag these as constraints core Prisma cannot express; enforcing only in application code leaves a race-condition window under concurrent requests, so the raw partial-unique index is the durable backstop and the service-layer check is the fast, friendly error path.

- **Task — Migration workflow:** `prisma migrate dev` for local, `prisma migrate deploy` for prod; add the raw partial-unique indexes above via a hand-edited `migration.sql` in the generated migration folder (already documented above each affected model in `schema.prisma`'s comments).
  - **Why:** Prisma's declarative schema can't express partial indexes, so this is the only way to get them into the actual database without forking the schema file itself.

- **Task — Seed workflow (`prisma/seed.ts`):** seed exactly one `PLATFORM_ADMIN` user for local/dev/staging bootstrap, using fixed credentials from environment variables:
  ```ts
  // prisma/seed.ts
  const email = process.env.ADMIN_EMAIL!;      // e.g. admin@platform.com
  const rawPassword = process.env.ADMIN_PASSWORD!; // never a literal in code
  const passwordHash = await bcrypt.hash(rawPassword, 12);
  await prisma.user.upsert({
    where: { email },
    update: {},
    create: { email, passwordHash, role: 'PLATFORM_ADMIN', isVerified: true },
  });
  ```
  Also seed reference Colleges/Departments/Courses for local dev only — never run this seed against production with dev fixture data.
  - **Why:** `userflow.md` has no Platform Admin registration flow at all (Section 16 §1) — the platform cannot exist without at least one Platform Admin, so seeding is the only compliant way to create the first account; using env vars (not a hardcoded email/password) keeps real credentials out of source control while still giving the team a fixed, known login for first access.

- **Task — Repository usage:** one repository file per model; repositories never `include`/`select` more than the calling service needs.
  - **Why:** keeps DTO shaping (and the responsibility to never leak `passwordHash`) entirely inside `services/`, so repositories stay dumb and reusable across features.

## 8. Error Handling

- **Custom error classes (`errors/`):** `ValidationError (400)`, `AuthenticationError (401)`, `AuthorizationError (403)`, `NotFoundError (404)`, `ConflictError (409)` — business-rule/state violations (e.g. "resource not in Approved state"), `DatabaseError (500)` — wraps Prisma errors, never exposes Prisma's raw message to the client.
- **Centralized error middleware:** last middleware in the chain; maps each custom error to the standard error envelope (Section 4); logs full error server-side (Winston/Pino) but returns only `code` + `message` (+ `fields` for validation) to the client.
- **Never** let an unhandled Prisma error (e.g. unique constraint violation) reach the client raw — catch at repository or service boundary and rethrow as `ConflictError`/`ValidationError` with a clean message.
- **Operational vs unexpected:** operational errors (validation, business rule, auth) are expected and logged at `warn`; unexpected errors (bugs, DB connection loss) logged at `error` with stack trace server-side only.

## 9. Logging

- **Request logging:** method, path, status, duration, `userId` (if authenticated) — via middleware, one line per request.
- **Error logging:** stack trace + context, server-side only, never in the HTTP response.
- **Security logging:** failed logins, authorization denials, ownership-check failures — flagged distinctly for later audit.
- **Audit logging:** every `AdminOverrideLog` write is also mirrored to the application log at `info` level (in addition to the DB row, which is the durable record of truth per §7.5).
- **Performance logging:** slow-query warnings (configurable threshold) for Prisma calls.
- **Never** log `passwordHash`, raw passwords, JWT secrets, or full JWT tokens.

## 10. Security Rules

- **Helmet:** enabled globally.
- **Rate limiting:** per-IP on `/auth/*` endpoints (login, forgot-password, register) to blunt brute force/enumeration.
- **CORS:** allow-list the Next.js frontend origin(s) only, `credentials: true` (required — auth cookies must be sent cross-origin between the Next.js frontend and this API, per the cookie decision in Section 16 §6).
- **Input sanitization:** trim/normalize strings server-side; never interpolate user input into raw SQL (Prisma parameterizes by default — never use `$queryRawUnsafe` with unsanitized input).
- **SQL injection prevention:** Prisma Client only; if a raw partial-unique-index migration is needed (Section 7), it is static DDL, not per-request user input.
- **XSS prevention:** treat all free-text fields (`title`, `description`, `tags`, moderator/decision reasons) as untrusted on output — frontend's responsibility to escape on render, backend must not execute or transform them as HTML.
- **JWT security:** short-lived access tokens, separate signing secret for refresh tokens, `iss`/`aud`/`exp` claims validated on every verify.
- **Password rules:** minimum length + complexity enforced via Zod at register/reset time; bcrypt cost factor ≥ 12.
- **Secure cookies (confirmed — Section 16 §6):** both access and refresh tokens are delivered as `httpOnly`, `secure`, `sameSite=strict` cookies — chosen over bearer tokens since the frontend is Anthropic's own first-party Next.js app, and httpOnly cookies keep tokens out of reach of any XSS in the frontend.
- **CSRF (mandatory, not optional):** because auth now lives in cookies, every state-changing request (`POST`/`PATCH`/`DELETE`) must carry a CSRF token via `X-CSRF-Token` header, verified against a non-httpOnly CSRF cookie issued at login (double-submit pattern) — implemented in Phase 2, task 5.
- **Environment security:** `.env` never committed; `config/env.ts` validates presence/shape at boot and crashes fast if missing.
- **Secrets handling:** JWT secrets, DB URL, SMTP credentials only via env vars, never hardcoded, never logged.

### Phase 2 — Authentication Core
1. Bcrypt password hash/compare utility (`auth/password.ts`).
2. JWT access-token sign/verify utility (`auth/jwt.ts`).
3. Refresh-token sign/verify utility (`auth/jwt.ts`, separate secret — stateless, Section 16 §1).
4. Cookie helper (`auth/cookies.ts`) — sets/clears `accessToken`, `refreshToken` (both `httpOnly`, `secure`, `sameSite=strict`) and a separate non-httpOnly `csrfToken` cookie.
5. `csrfGuard` middleware (`middlewares/csrf.ts`) — compares `X-CSRF-Token` header against the `csrfToken` cookie on every `POST`/`PATCH`/`DELETE`.
6. Login `POST /api/v1/auth/login` (email + password, any `Role`) — sets the three cookies (task 4); response body is only the user profile DTO (never `passwordHash`, never the raw tokens).
7. Refresh `POST /api/v1/auth/refresh` — reads the `refreshToken` cookie, rotates and reissues both cookies.
8. Logout `POST /api/v1/auth/logout` — clears all three cookies (`maxAge=0`); document the statelessness limitation (Section 16 §1: cannot force-expire a still-valid refresh token server-side before it naturally expires).
9. Forgot Password `POST /api/v1/auth/forgot-password` — emails a signed reset link via Nodemailer.
10. Reset Password `POST /api/v1/auth/reset-password` — verifies signed token, updates `passwordHash`.
11. `authenticate` middleware wired globally on protected router group; `csrfGuard` wired on all state-changing routes.
12. Manual/integration smoke test of the full login → refresh → logout cycle, including a CSRF-missing-header rejection test.

No other role (including Sub Admin) has create/edit authority anywhere in this hierarchy. Platform Admin's authority over `Resource` records themselves is handled separately, exceptionally, in Phase 15.

2. Department: `POST/GET/PATCH /departments` (platform-level, §2.1) — Platform Admin only.
3. CollegeDepartment "adoption": `POST /colleges/:collegeId/departments` (adopt), `DELETE /colleges/:collegeId/departments/:departmentId` (un-adopt) — Platform Admin only (confirmed, Section 16 §5).

5. Course: `POST/PATCH /departments/:departmentId/courses` — Platform Admin only; `PATCH` updates `name`/`description` only, never re-points existing resources (§7.4 course mutability rule) — a structurally different course must be a new row, never an overwrite.

### Phase 5 — User Registration & Identity

> **Confirmed flow (Section 16 §3):** a Student registers by selecting their college, department, and session (§1.2) and lands as `isVerified=false`. The actual verification step is **not** an automated email token — it is the CR/Co-CR of that exact Department+Session manually approving the registration, per §0.2 ("Verifies student registrations for their own batch") and §7.3. Bootstrap case: if no active CR/Co-CR exists yet for that Department+Session (e.g. the very first batch, before anyone has been appointed), the request falls to the Sub Admin of the college instead — mirroring the same "falls to Sub Admin until scope has an owner" pattern already used for queue transfers in §1.4/§1.5.

1. Student registration `POST /auth/register/student` (college, department — must be adopted by college per §8, session, `regNo` unique per `(collegeId, regNo)`, email, password) → creates `User(role=STUDENT, isVerified=false)`. **File:** `services/user.service.ts` (`registerStudent`), `repositories/user.repository.ts`.
2. Student verification queue — CR/Co-CR view `GET /cr/student-verifications` (CR/Co-CR, scoped to their own Department+Session, `requireActiveCrCoCr` guard from Phase 3) — lists `isVerified=false` Students in that exact Department+Session. **File:** `services/studentVerification.service.ts`, `controllers/user.controller.ts`.
3. Student verification queue — Sub Admin fallback view `GET /sub-admin/student-verifications` (Sub Admin, own college only) — lists `isVerified=false` Students in any Department+Session of that college that currently has **no active CR/Co-CR** (bootstrap case). **File:** `services/studentVerification.service.ts` (shared query, different scope filter).
4. Verification approval `POST /student-verifications/:userId/approve` (CR/Co-CR of the matching Department+Session, or Sub Admin of the college when no CR/Co-CR is active for it) → sets `isVerified=true`; reject with `403` if the caller's scope doesn't match the target student's Department+Session. **File:** `services/studentVerification.service.ts`, guarded by scope checks from Phase 3.
5. Block all upload/report/self-deletion actions while `isVerified=false` (§1.2) — enforced as a shared precondition check in `services/resource.service.ts` and `services/report.service.ts`, not duplicated per-route.
6. Teacher registration `POST /auth/register/teacher` (college, one-or-more departments, email, password) → creates `User(role=TEACHER, teacherVerificationStatus=PENDING_VERIFICATION)` + `TeacherDepartment` rows. **File:** `services/user.service.ts` (`registerTeacher`).
7. Platform Admin account provisioning — **no public endpoint**: seeded only, via Phase 1 task 11 / `prisma/seed.ts` (Section 16 §1).
8. Sub Admin account provisioning — **no public self-registration**: an existing user is *promoted* to Sub Admin by Platform Admin in Phase 6, not created fresh here (Section 16 §2).
9. Profile read `GET /users/me` — role-specific DTO shaping (never leak `passwordHash`). **File:** `controllers/user.controller.ts`.

### Phase 6 — Role Assignments
1. Teacher verification queue `GET /sub-admin/teacher-verifications` (Sub Admin, own college only) + `POST /sub-admin/teacher-verifications/:userId/approve` → sets `teacherVerificationStatus = VERIFIED` (§5.8).
2. Sub Admin appointment — **promotion, not creation** (Section 16 §2): `POST /platform-admin/sub-admins` (Platform Admin; body: `userId` of an **existing** registered user belonging to the target college, e.g. a verified Teacher) → in one transaction, updates that `User.role = SUB_ADMIN` and creates the `SubAdminAssignment` row — enforce "one active Sub Admin per college" (Section 7). **File:** `services/subAdmin.service.ts` (`appointSubAdmin`), `repositories/user.repository.ts` + `repositories/subAdminAssignment.repository.ts`.
   - **Why a promotion, not a fresh account:** Platform Admin selects someone the college already trusts (an existing user), rather than the backend minting a brand-new identity out of nowhere.
   - **Consequence to implement carefully:** `schema.prisma`'s `User` model has no "previous role" field, so after a promotion there is no stored way to revert `role` back to `TEACHER`/`STUDENT` on revocation. Do **not** attempt to guess or store a shadow previous-role value. Instead, treat `SubAdminAssignment.isActive` as the actual source of truth for Sub-Admin authority (Section 6, task 10) — `User.role` staying `SUB_ADMIN` after revocation is a known, accepted side effect, not a bug (see Section 16 §2 for the full reasoning).
3. Sub Admin revocation `POST /platform-admin/sub-admins/:assignmentId/revoke` → sets `isActive=false`, `revokedAt`, transfers all open queue items (Pending Teacher uploads, In Review resources, pending promotion recommendations) to the incoming Sub Admin on next appointment (§1.5) — implement the transfer as part of the *appointment* transaction of the replacement, not the revocation (queue sits "unassigned" in between, per §1.5).
4. CR/Co-CR appointment `POST /sub-admin/cr-assignments` (Sub Admin, own college; body: userId (existing verified Student), departmentId, sessionId, type CR|CO_CR) — enforce "one active CR + one active Co-CR per (college, dept, session, type)" (Section 7).
5. CR/Co-CR revocation `POST /sub-admin/cr-assignments/:id/revoke` → sets `isActive=false`; any resource `In Review` in that CR/Co-CR's scope returns to `Pending` and transfers to Sub Admin's queue immediately (transaction); on next CR/Co-CR appointment for that Department+Session, auto-move undecided transferred items into the new CR/Co-CR's queue (§1.4).
6. Platform Admin emergency role appointment `POST /platform-admin/emergency-appointments` — appoints interim Sub Admin OR a CR/Co-CR directly (sets `CrCoCrAssignment.isEmergencyAppointment = true` for the latter case) — **always** writes an `AdminOverrideLog(overrideType=ROLE_APPOINTMENT)` row with required `justificationNote` (§1.4, §1.5, §0.2). See Section 16 §16.2.2 for the routine-vs-exceptional line drawn for this endpoint.

### Phase 7 — Resource Upload & Core CRUD
1. Resource create service skeleton (no moderation logic yet) — validates classification fields (resourceType, title, description, tags, courseId → departmentId derived, sessionId conditional on PYQ).
2. Storage adapter: Multer disk storage, path convention `storage/uploads/<collegeId|platform>/<resourceId>/<filename>`, MIME/size validation at Multer layer (§3.4).
3. Content hash computation on upload (for `contentHash` field) — used for dedup warning (§3.1) and safe-delete checks (§5.6, §8), not for blocking upload.
4. Student upload `POST /resources` (role=STUDENT, verified) → forces `visibility=COLLEGE`, `collegeId=own`, `state=PENDING`; returns duplicate-hash warning (non-blocking) if a match exists for `(collegeId, courseId, contentHash)` (§3.1).
5. Teacher upload `POST /resources` (role=TEACHER, VERIFIED only) → client chooses `visibility` (COLLEGE default or PLATFORM), `uploaderRoleSnapshot=TEACHER`, `state=PENDING`, always routes to Sub Admin regardless of visibility (§3.2).
6. Sub Admin / Platform Admin upload of platform-wide types (syllabus, PYQ, book PDF, video) `POST /resources` (§3.3) — Platform Admin uploads bypass Pending and are created directly `Approved` (§3.4).
7. YouTube-link video resource: allow `resourceType=VIDEO` with `youtubeUrl` instead of `fileUrl`, no Multer file required (§3.3).

10. My Uploads listing `GET /resources/my-uploads` — statuses per §3.9 table (Pending, In Review, In Review (Deletion Flagged) as a derived display label, Approved, Rejected, Deletion Requested, Deletion Denied as a derived display label, Deleted, Superseded).
11. Resource read `GET /resources/:id` — enforce §0.3 visibility matrix (guest/platform-only; student/teacher default-own-college + opt-in toggle; CR/Co-CR two-tier; Sub Admin own-college full + other-college read-only; Platform Admin full).
12. Metadata edit — lightweight `PATCH /resources/:id/metadata` (title/description/tags, uploader-only, no state change, §3.6).
13. Metadata edit — structural `PATCH /resources/:id/reassign` (courseId/departmentId change, uploader-only, department-scope validated per task 9) → transitions `Approved → Pending` and **invalidates any outstanding `PromotionRecommendation`** in the same transaction (§3.6, §5.4 invalidation rule).
14. Versioning `POST /resources/:id/versions` (uploader-only, regardless of current role, §3.5) → creates a new `Resource` row with `rootResourceId` set, `versionNumber` incremented, `state=PENDING`, inherits current `visibility` of the root/latest version (§3.5, §8 "version inheritance on promoted resources").
15. Version approval side-effect: when a new version is Approved, the prior version transitions to `SUPERSEDED` automatically (system transaction, §5.1, §3.5) — implement inside the moderation-approve service (Phase 9), referenced here for planning only.

### Phase 9 — Moderation
1. Resource state machine service (`resourceStateMachine.ts`) encoding exactly the transition table in §5.1 — every other moderation task calls into this, never mutates `state` directly.
2. CR/Co-CR queue `GET /cr/queue` — Pending Student `COLLEGE` uploads (+ resubmitted Rejected items) within the CR/Co-CR's own Department+Session only (§5.2, guard from Phase 3).
3. Sub Admin queue `GET /sub-admin/queue` — Pending Teacher uploads + Pending `PLATFORM` resources (any uploader role) + escalations, scoped to Sub Admin's own college (§5.3).
4. Open for review `POST /resources/:id/open-review` (moderator, Pending → In Review) — role/scope-guarded per queue ownership (§5.1 table).
5. Approve `POST /resources/:id/approve` (In Review → Approved, written reason optional) — if this is a v2 approval, trigger prior-version `SUPERSEDED` transition in the same transaction (§3.5, §5.1).
6. Reject `POST /resources/:id/reject` (In Review → Rejected, written reason **required**, §3.8) — notify uploader with reason.
7. Self-cancel (uploader) `POST /resources/:id/self-cancel` — only while `Pending` (Pending → Deleted, §3.7).
8. Deletion flag while In Review `POST /resources/:id/flag-deletion` (uploader) — sets `deletionFlag=true`, `deletionRequestedAt`, state stays `In Review` (§3.7); display label "In Review (Deletion Flagged)" is computed in the DTO layer, never stored as a state.
9. Combined resolution on flagged In Review item: moderator's `approve`/`reject` actions (tasks 5–6) must branch on `deletionFlag` — approve-deletion path → `Deleted` regardless of content verdict; deny-deletion path → normal Approve/Reject flow continues (§3.7, §8 race-condition rule).
10. Deletion request from Approved `POST /resources/:id/request-deletion` (uploader, Approved → Deletion Requested) — **invalidate any outstanding PromotionRecommendation** in the same transaction (§3.7, §5.4).
11. Deletion decision `POST /resources/:id/deletion-decision` (moderator; approve → Deleted; deny → Approved + `DeletionRequest.status=DENIED` logged with reason, surfaced in My Uploads, §3.9) — routing mirrors moderation queue routing (§5.7): Student COLLEGE → CR/Co-CR, Teacher/PLATFORM → Sub Admin.
12. Report-against-Deletion-Requested race condition `POST /resources/:id/report` when `state=DELETION_REQUESTED` → moves to `In Review`, retains the deletion flag, moderator resolves both together (§5.1, §8).
13. Physical file deletion safety check: on any transition to `Deleted`, only remove the on-disk file if no other `Resource` row shares the same `contentHash` (§5.6, §8) — implement as a repository-level guarded delete, never delete on state-write alone.
14. Re-submit `POST /resources/:id/resubmit` (Rejected → Pending, uploader).
15. CR/Co-CR role-revoked-mid-review sweep: on CR/Co-CR revocation (Phase 6 task 5), any `In Review` item in that scope returns to `Pending` and transfers to Sub Admin — implement as part of the revocation transaction, cross-referenced here.
16. Moderation audit `GET /sub-admin/cr-audit` — CR/Co-CR moderation throughput/decisions within Sub Admin's college (§5.3, §7.2).

### Phase 10 — Reporting
1. Report submit `POST /resources/:id/report` (any authenticated user, reason: INCORRECT/SPAM/PLAGIARISED, only against Approved or Deletion Requested resources, §5.5) — immediately hides resource from public listing and transitions to `In Review` (reuse state-machine service from Phase 9).
2. Report routing: `COLLEGE` Student resources → CR/Co-CR queue; Teacher uploads and `PLATFORM` resources → Sub Admin queue (§5.5, §5.7 pattern reused).
3. Report resolution `POST /reports/:id/resolve` (moderator; ties into the same approve/reject/deletion-decision actions from Phase 9 — a report itself has no independent "approve/deny," it is resolved by whatever content decision the moderator makes on the underlying resource) — set `Report.status=RESOLVED`, `resolvedById`, `resolvedAt`.
4. Report-triggers-promotion-invalidation: filing a report against a resource with an outstanding `PromotionRecommendation` invalidates it in the same transaction (§5.4 invalidation rule).

### Phase 11 — Promotion Workflow
1. Path A — Recommend `POST /resources/:id/recommend-promotion` (CR/Co-CR, own Dept+Session, resource must be `Approved` + `visibility=COLLEGE` + Student-uploaded) → creates `PromotionRecommendation(status=PENDING)`; enforce "one PENDING recommendation per resource" (Section 7).
2. Path A — Sub Admin decision `POST /promotion-recommendations/:id/approve` / `/deny` (Sub Admin, own college) → on approve: `Resource.visibility=PLATFORM`, create `PromotionEvent(path=PATH_A, action=PROMOTED)`, `PromotionRecommendation.status=APPROVED`; on deny: visibility stays COLLEGE, `PromotionRecommendation.status=DENIED`, **no `PromotionEvent` is created** (no visibility change occurred — see Section 16 §16.2.4). Notify per §3.8 (approve → uploader + recommending CR/Co-CR; deny → recommending CR/Co-CR only).
3. Path B — Direct promote `POST /resources/:id/promote` (Sub Admin, own college, resource must be `Approved` + Teacher-uploaded, no recommendation required) → `visibility=PLATFORM`, create `PromotionEvent(path=PATH_B, action=PROMOTED)`, **no notification sent** (§3.8, §0.2 Teacher).
4. Revoke `POST /resources/:id/revoke-promotion` (Sub Admin, own college, resource originated from their college) → `visibility=COLLEGE`, create `PromotionEvent(action=REVOKED)` with the correct original `path`.
5. Invalidation enforcement: verify (via tests) that structural edit (Phase 7 task 13), deletion request (Phase 9 task 10), and report (Phase 10 task 4) all invalidate an outstanding `PENDING` recommendation — `PromotionRecommendation.status=INVALIDATED`, `invalidatedAt`, `invalidationReason` set.
6. Re-promotion after resource returns to Approved requires a brand-new recommendation — verify no auto-resume logic exists anywhere (§5.4).
7. Version inheritance: verify (via tests) that a new version of a `PLATFORM` resource inherits `visibility=PLATFORM` and routes to Sub Admin queue regardless of uploader's current role (§8) — cross-reference Phase 7 task 14 and Phase 9 queue logic.
8. Promoted-then-rejected notification fan-out: on Reject (Phase 9 task 6) of a resource that has a `PromotionEvent`, notify per path — Path A: uploader + recommending CR/Co-CR + approving Sub Admin; Path B: promoting Sub Admin only (§3.8, §5.5).
9. Platform Admin exceptional promotion action `POST /platform-admin/promotion-override` (Path A decision or Path B promotion executed by Platform Admin instead of Sub Admin) → same effects as tasks 2/3 **plus** an `AdminOverrideLog(overrideType=PROMOTION_DECISION, justificationNote required)` row (§5.4a) — see Section 16 §16.2.2's routine-vs-exceptional reasoning (same principle applied to promotion decisions per §5.4a).

### 16.1 Confirmed by Product Owner

1. **Platform Admin account creation.** No registration flow exists in `userflow.md` for this role — confirmed as seed-only. `prisma/seed.ts` creates exactly one `PLATFORM_ADMIN` user from `ADMIN_EMAIL` / `ADMIN_PASSWORD` env vars, password bcrypt-hashed before insert (Section 7, Phase 1 task 11). Never a public endpoint, never a hardcoded literal email/password in code.
2. **Sub Admin account creation is a promotion, not a fresh registration.** Platform Admin selects an **existing** registered user (belonging to the target college) and promotes them: `POST /platform-admin/sub-admins` sets `User.role = SUB_ADMIN` and creates the initial `SubAdminAssignment` in one transaction (Phase 6, task 2). Because `schema.prisma`'s `User` model has no field to store a "previous role," a later revocation cannot revert `role` back automatically — Sub-Admin-gated routes must therefore authorize on an **active `SubAdminAssignment`**, not on `User.role` alone (Section 6, task 10), so a revoked user is functionally a normal user again even though their `role` column still reads `SUB_ADMIN`.
3. **Student verification is performed by CR/Co-CR, not an automated email token.** After registering (selecting college, department, session per §1.2), a Student sits at `isVerified=false` until the CR/Co-CR of that exact Department+Session approves them (§0.2, §7.3 — "Verifies student registrations for their own batch"). **Bootstrap fallback:** if no active CR/Co-CR yet exists for that Department+Session (e.g. the very first cohort, before any appointment has happened), the verification request routes to the Sub Admin of the college instead — the same "falls to Sub Admin until the scope has an owner" pattern already used elsewhere in the spec for queue transfers (§1.4, §1.5). No upload, report, or self-deletion action is permitted while `isVerified=false` (§1.2). See Phase 5, tasks 2–5.
4. **File upload limit is fixed at 20 MB per file.** `MAX_FILE_SIZE_MB=20` in `.env`, enforced via Multer's `limits.fileSize` (Section 4). MIME whitelist remains config-driven (`ALLOWED_MIME_TYPES`) with the documented default list in Section 4 — exact list can still be adjusted by the product owner without touching code, only the env var.
5. **Platform Admin's master-data authority is confirmed exactly as scoped:** Colleges → adopted Departments → Sessions (per department) → Courses (per department) are all Platform-Admin-only to create/edit (§7.1), plus Platform Admin's separate, exceptional CRUD authority over `Resource` records via the Phase 15 override. No other role gains master-data authority anywhere in the system; Sub Admin's authority stays scoped to moderation, verification, and role-assignment within their own college only.
6. **Access/refresh tokens are delivered via httpOnly cookies, not bearer tokens.** Both `accessToken` and `refreshToken` are `httpOnly`, `secure`, `sameSite=strict` cookies (Section 6, Phase 2). Because auth now lives in cookies, CSRF protection is **mandatory**: a non-httpOnly `csrfToken` cookie is issued at login and must be echoed via `X-CSRF-Token` header on every state-changing request, verified by `csrfGuard` (Section 10, Phase 2 task 5).

### 16.2 Remaining Assumptions (still genuinely unspecified)

1. **Refresh, password-reset, and email-verification-link tokens have no backing DB table** (`schema.prisma` defines no such model). **Assumption:** all three are short-lived, signed, stateless JWTs — refresh tokens verified by signature + expiry only, reset/verification links likewise. **Limitation:** none of the three can be individually revoked before natural expiry without adding a persistence layer, which would mean adding a model not present in `schema.prisma` — flagged here rather than silently doing that.
2. **Routine vs. exceptional line for Platform Admin's role-appointment actions.** `schema.prisma` only carries an `isEmergencyAppointment` flag on `CrCoCrAssignment`, not on `SubAdminAssignment`. **Assumption:** normal Sub Admin appointment/promotion (Phase 6, task 2) is always routine and does **not** write an `AdminOverrideLog` row; only a Platform Admin appointing a CR/Co-CR *directly* (bypassing Sub Admin, §1.4 emergency exception) is exceptional and writes `AdminOverrideLog(overrideType=ROLE_APPOINTMENT)` — matching the schema's explicit `isEmergencyAppointment` flag placement.
3. **`AdminOverrideLog.targetType` / `.action` are free-text strings in the schema, not enums.** **Assumption:** a fixed application-layer whitelist (`constants/adminOverrideActions.ts`) constrains allowed values per `overrideType` to prevent inconsistent audit data — an app-layer constraint only, not a schema change.
4. **Deny outcome of a Path A promotion recommendation does not create a `PromotionEvent` row** (no visibility action occurred) — only `PromotionRecommendation.status` changes to `DENIED`. This is an inference from `schema.prisma`'s comment that `PromotionEvent` logs "every visibility change and why," not every decision; flagged here since it's easy to mis-implement as always creating an event.
